# Clinic Scheduling System

A production-shaped appointment scheduling system for a small medical
clinic: a booking API, two-way Google Calendar sync, and a chatbot
(SMS + voice) that patients can use to book, check availability, and
cancel — with an identity and safety model designed to survive prompt
injection, not just handle the happy path.

Built solo, phase by phase, with every phase closed only after
verification against the real stack (real Postgres, real Twilio
signatures, real Google Calendar, real Gemini API) — not passing tests
in isolation. That discipline, and what it caught, is most of what
makes this project worth reading past the feature list. See
[**Why this project is worth reading**](#why-this-project-is-worth-reading)
below.

## What it does

- **Booking engine** — patients, doctors, time slots, appointments.
  Double-booking is prevented structurally (a partial unique index plus
  `SELECT ... FOR UPDATE`), not by application-level "check then book"
  logic that a race condition can slip through.
- **Two-way Google Calendar sync** — a doctor's personal calendar
  blocks availability; bookings push back out as calendar events.
  OAuth2+PKCE, tokens encrypted at rest, automatic refresh serialized
  against concurrent workers.
- **A chatbot patients can actually use**, over SMS and voice, that:
  - identifies a caller by phone number and **authenticates** with date
    of birth — two different things, treated as two different things
  - locks out after three failed attempts, server-side, so the model
    can't be talked into believing a different count
  - never lets the model name a patient, a phone number, or a
    conversation — every tool call is scoped by the transport layer,
    not by anything the model says
  - commits nothing in one shot: booking and cancelling are
    propose-then-confirm, single-use, so a repeated or injected message
    can't cause a double action
  - on voice specifically, never checks a spoken date of birth against
    a patient record until the caller has confirmed it was heard
    correctly — a speech-to-text error costs nothing, only a
    caller-confirmed value is ever treated as a real guess
- **Staff-facing safety valves** — escalation pages a real person,
  terminal conversations can be deliberately reopened without ever
  resurrecting a prior identity, both enforced at the schema level, not
  just in application logic.

## Why this project is worth reading

The feature list above is standard CRUD-plus-integrations work. What
isn't standard is how many times this project's own stated conventions
caught a real problem before it shipped — including, once, a problem in
the AI collaboration process itself.

**Standing conventions, applied repeatedly, not just stated once:**

- **Assert state, not text.** A chatbot refusing to act is not proof it
  refused — the tests assert what changed in the database (an attempt
  counter, a lockout, a null `patient_id`), never just the reply text.
  ([`tests/test_injection_suite.py`](tests/test_injection_suite.py))
- **Verify a test's premise, not just its outcome.** A passing test
  that exercises a cold identity map, a concurrent race, or a crash
  mid-transaction is only meaningful if the premise (the map really was
  cold, the race really was contested, the crash really landed where
  claimed) is checked independently — not assumed because the assertion
  passed.
- **Audit the whole config surface, not just the instance that already
  bit you.** Test and production sessions are built from the *same*
  factory function (`app/db/session.py`) specifically so autoflush,
  `expire_on_commit`, and connection settings can't silently drift
  between what's tested and what runs — after they once did.
- **An unenforced invariant is not an invariant.** A comment asserting
  "this can never happen" is evidence nothing actually checks it, not
  evidence it's safe — this reframe came directly out of finding a real
  gap that a comment had been quietly asserting away.

**Concrete catches, not hypothetical ones:**

- **The lockout-bypass finding** ([injection suite, finding
  #10](tests/test_injection_suite.py)) — an escalated conversation could
  be silently reactivated just by texting again, resetting the 3-strike
  counter to zero. An attacker didn't need to break the lockout; they
  only needed to keep texting. Fixed by making terminal conversation
  states permanent for that phone number, with a deliberate staff-only
  reopen path (below) so the fix didn't just trade one lockout for
  another.
- **`alembic check` cannot see CHECK constraints or index predicates**
  ([migration `0009`](alembic/versions/0009_escalation_notify.py)) —
  discovered by hand-reviewing every autogenerated migration against
  the models rather than trusting the diff, which is now enforced in CI
  by a purpose-built script
  ([`scripts/check_schema_drift.py`](scripts/check_schema_drift.py))
  that Alembic's own tooling doesn't provide.
- **`FOR UPDATE` without `populate_existing` isn't actually locking**
  ([`conversation_service.load_active_conversation`](app/services/conversation_service.py))
  — the lock is acquired correctly, but SQLAlchemy's identity map hands
  back a stale cached row anyway, which caused a real, reproducible lost
  update under concurrency (roughly 1 run in 5) before being caught.
- **A Gemini verification episode**, told in full in
  [`docs/engineering-notes.md`](docs/engineering-notes.md) — a claim
  about whether an API key and model were real was made confidently,
  reversed confidently, and reversed again, before finally being
  settled with raw evidence (a TLS certificate chain, an HTTP response
  body, a directly-quoted live documentation fetch) instead of another
  explanation. The interesting part isn't the technical fix — it's that
  the project's own verification discipline held up when turned on the
  AI collaboration process itself, mid-conversation, under direct
  pressure from the person paying attention. Worth reading on its own.

**Decision records, written before the code, corrected after it, both
kept:**

- [`docs/phase-4-voice-transport-decision.md`](docs/phase-4-voice-transport-decision.md)
  — webhook-per-turn vs. a full streaming media pipeline for voice,
  decided with an explicit cost/structure comparison before any code,
  then corrected in place once live measurement showed the deferred
  mitigation (a poll/redirect hold pattern) was needed sooner than
  planned — the correction is in the same file, not a rewrite.
- [`docs/phase-4-dob-over-voice-decision.md`](docs/phase-4-dob-over-voice-decision.md)
  — why a misheard date of birth over voice is a different failure mode
  than a typo over SMS, and why the fix belongs in the identity service
  as a structural gate rather than as a prompt instruction trusting the
  model to ask twice.
- [`docs/security-no-authentication.md`](docs/security-no-authentication.md)
  — a running risk register, not a one-time audit: what's mitigated,
  what's deliberately deferred and at what trigger condition, and one
  credential (`TWILIO_AUTH_TOKEN`) called out as categorically more
  dangerous than the others it sits next to in a rotation table, with
  the reasoning spelled out rather than assumed obvious.

## Architecture, briefly

```
app/
  api/v1/          FastAPI routes — appointments, calendar, auth, webhooks
  services/         business logic: booking, calendar sync, identity,
                     notifications, proposals, the voice/SMS outboxes
  chatbot/           the conversation loop, tool dispatch, prompts
  integrations/      Gemini, Google Calendar, Twilio/SendGrid senders
  models/            SQLAlchemy models — one file per table
  worker.py          the background job scheduler (APScheduler)
alembic/versions/     hand-reviewed migrations (12, each with a note on
                       what autogenerate caught vs. missed)
tests/                 ~300 tests, real Postgres, real HTTP, no mocked DB
docs/                  decision records and the risk register above
```

Four phases, each closed only after live verification:

1. **Core booking engine** — race-safe booking/cancel, Postgres-specific
   correctness (partial indexes, row locks).
2. **Calendar sync + notifications** — OAuth2, two-way sync, a unified
   outbox pattern reused three more times later in the project.
3. **The chatbot** — Gemini-backed conversation loop, structural
   injection defenses, staff auth, an 11-scenario adversarial test suite
   proving the safety model against the live pipeline (finding #10
   above came out of this).
4. **Voice** — a second transport for the same chatbot core, a real
   decision on webhook-per-turn vs. streaming, and a poll/redirect hold
   pattern built only after live measurement proved it was actually
   needed, not preemptively.

## Running it

```bash
cp .env.example .env   # fill in Twilio / Google / Gemini credentials
docker compose up -d
docker compose exec api alembic upgrade head
```

API on `localhost:8000`, Postgres on `localhost:5434` (5432 is commonly
already taken locally). Create a staff account with
`python scripts/create_staff_account.py` before hitting any
authenticated endpoint.

```bash
# tests (spins its own Postgres via TEST_DATABASE_URL, see tests/conftest.py)
docker compose exec api pytest -q

# schema drift check CI relies on -- catches what `alembic check` can't
python scripts/check_schema_drift.py --migrated <url> --models <url>

# diagnose the Gemini wire format against the live API directly
python scripts/smoke_test_gemini.py
```
